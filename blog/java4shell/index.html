What Java Teams Should Do About Java4Shell

Nimret Singh Sandhu · November 17, 2026 · 2 min read

A critical Java vulnerability disclosed today needs attention from any company running Java in production.

Researchers at Calif published details of Java4Shell (CVE-2026-114938), a memory-corruption flaw in OpenJDK’s Base64 decoder rated 9.2 out of 10. On affected servers, an attacker with no credentials can read heap memory, which may expose keys, tokens or customer data. In some products the flaw leads to remote code execution. The researchers demonstrated unauthenticated attacks on default installs of Jira, Confluence, Jenkins, Keycloak, Artifactory and PingFederate.

Who is exposed

A server is exposed when two conditions are true.

  • It runs OpenJDK 17.0.6 or later, including the Corretto, Temurin, Zulu, Red Hat, Microsoft and Oracle builds
  • Its x86-64 processor supports AVX-512 VBMI, which covers recent Intel Xeon and AMD Zen 4 chips (ARM servers are not affected)

What to do now

Oracle shipped fixed builds today, and other vendors are following on their own schedules. Until you can upgrade, the JVM flag -XX:-UseBASE64Intrinsics switches off the vulnerable code path. No attacks have been reported yet, but that window usually closes quickly once exploits circulate.

Upgrading Java is the easy step. Most of the effort goes into finding every runtime across containers, build images, vendor tools and appliances, then shipping the fix without breaking anything for customers.
