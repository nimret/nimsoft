The AI Wrote the Code Perfectly. That Was the Problem.

Nimret Singh Sandhu · October 20, 2026 · 5 min read

A few weeks ago, a developer was handed what looked like a routine feature request. The system needed to calculate filing deadlines automatically. A user enters a case event, and the software tells them when the next response is due.

The requirements document ran about two pages. The developer pasted it into an AI coding assistant, and within minutes had several hundred lines of clean, well-commented code. It compiled. It passed the handful of unit tests the assistant also wrote. The pull request looked tidy, and it went into review feeling nearly finished.

It wasn’t close to finished.

What the requirements were really saying

Buried in those two pages were rules that interacted with each other in ways nobody had mapped out. Deadlines varied by case type. They varied by jurisdiction. They shifted depending on how a document was served, whether by hand, by mail, or electronically. A deadline landing on a weekend or court holiday rolled forward, but each jurisdiction kept its own holiday calendar. Certain events paused the clock entirely, and an amended filing could reset it.

Each rule was simple on its own. Together they formed a decision space that no one had actually counted. Six case types across fourteen jurisdictions and three service methods already gives you 252 distinct paths before you add a single date. Layer in holidays, clock pauses, and resets, and the meaningful combinations climb into the thousands.

The AI didn’t flag any of this. It had no reason to. It was asked to implement the rules, and it implemented them faithfully, in the order they appeared, with reasonable assumptions wherever the text was vague. Where two rules conflicted, it quietly picked one. Where the document was silent, it filled the gap with something plausible.

Why testing became impossible

The problem surfaced when QA tried to build a test plan. To confirm the code was correct, they needed to know what correct looked like for each combination. Nobody could tell them. The developer didn’t know, because the developer had never worked through the logic. The product owner didn’t know either, because the requirements had been assembled from several sources and no one had resolved where they overlapped.

So the team faced an uncomfortable truth. They had working code with no way to say whether it worked. The tests the AI wrote only checked that the code did what the code did. They couldn’t catch a wrong interpretation, because the wrong interpretation was baked into both.

In a deadline system, a quiet error isn’t cosmetic. A miscalculated date can cause someone to miss a legal obligation. The feature was pulled back, the requirements were reworked from scratch with subject matter experts, and most of the generated code was thrown away.

The real lesson

It’s tempting to read this as a story about AI getting something wrong. It isn’t. The AI did exactly what it was told, and did it quickly and competently. The failure happened before the first prompt was typed.

Writing code has never been the hardest part of building software. The hard part is understanding the problem well enough to know what the code should do, where the edge cases live, and how you’ll prove it behaves correctly. That work used to happen almost by accident. A developer writing a deadline calculator by hand would hit the jurisdiction question on day one, get stuck, and go ask someone. The friction forced the understanding.

AI removes that friction. That’s its value, and also its danger. When code arrives instantly, nothing slows you down long enough to notice you don’t understand what you’re building.

The research is starting to reflect this. A 2025 randomized study by METR found experienced open-source developers were about 19 percent slower when using AI tools, even though they believed they were working faster. Veracode’s 2025 analysis of AI-generated code found that roughly 45 percent of samples introduced security weaknesses. Speed and confidence are not the same as correctness.

What I’d ask of any team using these tools

None of this is an argument against AI in software development. I use it, and my teams use it. It’s an argument about where human judgment has to sit. A few practices make the difference.

  • Model the problem before you prompt. If the requirements contain branching rules, draw the decision table first. If you can’t fill it in, you aren’t ready to generate code.
  • Write acceptance criteria independently of the AI. Tests written by the same tool that wrote the code will share its blind spots. Expected outcomes should come from people who understand the domain.
  • Treat ambiguity as a blocker, not a detail. Every place the AI had to guess is a place a defect may be hiding. Find those gaps and resolve them with the business.
  • Size testing effort against complexity, not lines of code. A small amount of generated code can carry an enormous verification burden.
  • Hold developers accountable for understanding, not just output. “The AI wrote it” should never be an acceptable answer in a code review.

AI has made writing software dramatically cheaper. It hasn’t made understanding software any cheaper at all. The teams that thrive will be the ones that recognize the difference, and invest their saved time in the thinking that AI can’t do for them.
